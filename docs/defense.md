# Подготовка к защите

## Демонстрация (примерно 7–10 минут)

1. Запустить run.cmd, открыть статистику (6): 5 клиентов, 8 предметов, 10 заявок, выручка завершённых аренд 6300 руб. Эти числа относятся к свежей демонстрационной базе.
2. Просмотреть три таблицы через пункт 8. Показать docs/er-diagram.svg: одна заявка относится к одному клиенту и одному предмету, у каждого клиента и предмета может быть много заявок в истории.
3. Показать поиск заявок по «Иванов» и «Перфоратор» (4 → 4/5).
4. Фильтры по статусу и дате (5 → 3/4). Сортировки заявок по дате и стоимости (3 → 7).
5. Создать заявку для клиента 1, предмета 6, с сегодняшней до завтрашней даты. Показать рассчитанную стоимость и занятость предмета.
6. Попробовать повторную заявку на тот же предмет: ошибка. Попробовать нулевой срок и несуществующего клиента.
7. Для созданной заявки показать запрещённый переход прямо в COMPLETED, затем CREATED → ACTIVE → COMPLETED. Предмет снова доступен.
8. Создать ещё заявку и изменить её даты: сумма пересчитывается в сервисе. Удалить её: предмет освобождается.
9. Экспортировать заявки в Excel (7 → 3), открыть exports/rentals.xlsx.
10. Показать verify.ps1 и итог проверки. После действий статистика закономерно отличается от первоначальной.

## Что объяснить в коде

- **Инкапсуляция:** поля моделей private; доступ идёт через методы.
- **Интерфейс:** Repository описывает CRUD независимо от способа хранения.
- **Полиморфизм:** ClientService вызывает методы Repository<Client,Integer>, а выполняется ClientRepository.
- **Наследование:** JDBC-репозитории наследуют общий код JdbcRepository и реализуют собственный map(ResultSet).
- **Enum:** RentalStatus хранит названия и проверяет допустимость перехода.
- **Сервис:** проверяет предметные правила независимо от меню. Сервис нельзя обойти, передав другой totalCost или статус в updateRental.
- **JDBC:** Connection — соединение, PreparedStatement — запрос с параметрами, ResultSet — результат.
- **Параметры:** значения пользователя передаются через setObject, не склеиваются с SQL. Динамические фрагменты сортировки берутся только из фиксированных ASC/DESC.
- **Ресурсы:** try-with-resources закрывает ResultSet, PreparedStatement и собственное соединение. Соединение транзакции закрывает DatabaseConnection.
- **Транзакция:** создание заявки и изменение доступности — единая операция. При исключении rollback; при успехе commit.
- **Конкуренция:** SELECT FOR UPDATE сериализует бронирования одного предмета. Дополнительно частичный UNIQUE индекс запрещает две открытые заявки.
- **Связи:** FK защищает ссылочную целостность, RESTRICT не допускает скрытого удаления истории.
- **Коллекции:** List для результатов, Stream API/Comparator для сортировок, distinct для категорий, reduce для выручки.
- **Исключения:** BusinessException — бизнес-правило, EntityNotFoundException — отсутствующий ID, DataAccessException — ошибка инфраструктуры с сохранённой причиной.
- **Экспорт:** Apache POI создаёт настоящий XLSX; CSV — текстовый UTF-8 файл с правилами экранирования.

## Принятые упрощения

Каждый предмет бронируется одной открытой заявкой целиком; календарного расписания нескольких будущих аренд нет. Дата окончания не включается в число оплачиваемых дней. Просрочка устанавливается вручную. Тариф при редактировании CREATED берётся из текущей цены оборудования. Выручка — сумма завершённых аренд, без отдельного учёта платежей и штрафов. Доступность false также может означать ручной вывод из проката.

До защиты каждый участник должен уметь объяснить весь поток UI → Service → Repository → DB, даже если распределение рассказа внутри команды разное.
